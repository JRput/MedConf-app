# MedConf Website — Code & Architecture Audit

Scope: `medconf-website/src/**`, `package.json`, `next.config.ts`, `../supabase_schema.sql`. Read-only audit.

---

## 1. Architecture map

**Stack:** Next.js 16.1.6 (App Router), React 19.2.3, Tailwind v4 (`@import "tailwindcss"` in `globals.css`, no `tailwind.config` — v4 CSS-first config), `@supabase/ssr` 0.8 + `@supabase/supabase-js` 2.95, `lucide-react`. No state library, no data-fetching library (no React Query/SWR), no test setup (`package.json` has no test script/framework).

### Routes (all under `src/app/`)
| Route | File | Client/Server | Protected |
|---|---|---|---|
| `/` | `app/page.tsx` | not read in this pass | no |
| `/conferences` | `app/conferences/page.tsx` | **client** (`'use client'`) | no |
| `/conferences/[id]` | `app/conferences/[id]/page.tsx` | **client** | no |
| `/saved` | `app/saved/page.tsx` | **client** | yes |
| `/settings` | `app/settings/page.tsx` | not read | yes |
| `/dashboard`, `/dashboard/notifications` | not read | presumed client | yes |
| `/onboarding` | not read | presumed client | yes |
| `/auth/{login,signup,verify,callback}` | `callback/route.ts` is a server Route Handler; others presumed client | login/signup gated off when signed in |

**Every data-bearing route is a client component.** There is no server component doing a Supabase fetch (no RSC data fetching, no `generateStaticParams`, no streaming/suspense boundaries). This means: no SSR content for SEO on `/conferences` or `/conferences/[id]` (CLAUDE.md flags SEO as a reason the directory is public, but the directory renders empty until client JS runs and fetches), and every navigation pays a full client-side fetch + hydration cost.

### Data fetching
- `useConferences` (`src/hooks/useConferences.ts:108-143`): on mount, fires 4 parallel Supabase queries — **all conferences** (`select('*')` with only `archived=false` filter, no `.limit`), **all pricing_tiers** (`select('*')`, zero filters), **all course_sessions** (`select('*')`, zero filters), and active `scraper_sources`. All three big tables are paginated client-side via `fetchAllPages` (`src/lib/fetch-pages.ts`) in 1000-row chunks up to a 50,000-row safety cap, because Supabase's `db_max_rows` caps a single `.range()` at 1000.
- `/conferences/[id]/page.tsx:25-41` re-fetches conference + pricing_tiers + course_sessions **scoped by id** on every detail-page visit — this one IS filtered server-side (good), unlike the list page.
- `/saved/page.tsx:36-86` re-implements the same "fetch saved ids → fetch all matching conferences/pricing/sessions" pattern independently of `useConferences`/`useSaved`, with its own local state and its own pagination calls (`.in('id', ids)` — filtered, good).
- **All filtering, sorting, and searching happens client-side in JS** (`useConferences.ts:158-213`: `.filter()`/`.sort()` over the full in-memory array), not via Postgres queries. Same in `/saved`. There is no DB-side `ilike`/full-text search, no server-side pagination of the *displayed* list — the whole dataset is downloaded, then sliced in the browser.
- No caching layer: every mount re-fetches from scratch (no SWR/React Query, no `sessionStorage` cache, no Next `fetch` cache since these aren't `fetch()` calls but Supabase JS client calls, which Next's data cache doesn't intercept anyway).

### State management
- Local `useState`/`useEffect`/`useMemo` per hook/page. No global store, no context beyond what `@supabase/ssr` implies.
- **Filter state lives in the URL** (`useConferences.ts:46-72`, `readFiltersFromUrl`/`writeFiltersToUrl`), synced via `router.replace(..., { scroll: false })` — this is a good pattern (shareable/bookmarkable filtered views, back-button friendly within reason since `replace` doesn't push history entries per keystroke).
- `/saved/page.tsx` filter/sort state is local only, NOT in URL — inconsistent with `/conferences`.

### Auth flow
- `useAuth` (`src/hooks/useAuth.ts`): wraps `supabase.auth.getSession()` + `onAuthStateChange`, exposes `signUp`/`signIn`/`signOut`. Every component that needs auth (`useSaved`, `ReminderPanel`, `Navbar`) calls `useAuth()` independently → each mounts its own `createSupabaseClient()` (new browser client instance) and its own `onAuthStateChange` subscription. Not catastrophic (Supabase client is lightweight and shares the same localStorage session under the hood) but it's N redundant auth listeners on any page using multiple of these hooks.
- Route protection is server-side in `middleware.ts` using `createServerClient` + cookies, checking `auth.getUser()` and a `user_profiles.profile_completed_at` gate for onboarding — this part is solid (real server-side check, not just client redirect).
- `src/app/auth/callback/route.ts` — the only actual Server Route Handler in the app (OAuth/email-confirmation callback), not reviewed in depth this pass.

## 2. Performance & correctness risks

**High severity**

1. **Fetching the entire dataset client-side on every `/conferences` visit.** `useConferences.ts:114-119` pulls ALL rows of `conferences`, `pricing_tiers`, and `course_sessions` with no filters beyond `archived=false`, unconditionally, on every mount, with manual pagination working around Supabase's 1000-row cap. At today's ~44 active sources (per recent commits — CLAUDE.md's "23 sources" is stale) this is already multiple round-trips per table per page load, done in the browser, blocking first meaningful render behind 3+ sequential-feeling network waterfalls (well, `Promise.all` so parallel, but each of the big two is itself N sequential 1000-row page fetches inside `fetchAllPages`). This scales linearly with data size and caps out expensively — it's a ticking time bomb as source count and historical volume (course sessions especially) grows. No server-side filtering/search/pagination exists at all.
2. **No caching / re-fetch on every mount.** Navigating `/conferences` → `/conferences/42` → back to `/conferences` re-runs the full 3-table fetch from zero. No `sessionStorage`/router cache/SWR — a full waterfall every time.
3. **`/saved` duplicates ~all of `useConferences`'s fetch/pagination/grouping logic** (`app/saved/page.tsx:36-86`) instead of reusing a shared data hook. Two independent code paths to the same tables means any future schema change (e.g. new pricing column) has to be fixed twice, and they already use different source queries (`/conferences` fetches society + all columns from `scraper_sources`; `/saved` fetches only `id, source_name`).

**Medium severity**

4. **`price_gbp` typed as `number` but is a `DECIMAL(10,2)` column carrying non-GBP currencies** (per `lib/types.ts:79-82` comment and `conference-helpers.ts:46-58`) — Supabase JS returns `numeric` as a string in some configurations; worth confirming the client actually gets a JS number, not a string that `.toFixed()`/`Math.min()` would silently coerce. `PricingTable.tsx:173` calls `.toFixed(2)` directly on `tier.price_gbp assuming number — if Postgrest ever returns numeric as string (common gotcha), this throws at runtime. Not verified broken, but a real footgun given DECIMAL columns.
5. **`ConferenceCard` recomputes filtering-adjacent logic per card** (min/max price via `Math.min(...tiers.map(...))`, days-until-deadline regex parsing of `abstract_deadline_note` at `ConferenceCard.tsx:121-126`) — fine at current scale (hundreds of cards), but all of this re-runs on every parent re-render since none of it is memoized per-card (no `React.memo` on `ConferenceCard`, no `useMemo` inside it). With client-side filtering re-running `.filter()+.sort()` over the full array on every keystroke in the search box (`SearchBar` → `setFilters` → `useMemo` deps on `filters` object identity, which changes every call), every character typed re-renders and re-derives every visible card. Likely fine today, will visibly lag as row count grows.
6. **No loading skeletons** — every page shows a centred spinner (`Loader2` + "Loading…" text) instead of skeleton cards (`globals.css:152-161` even defines an unused `.skeleton` shimmer class — dead CSS, or intended-but-not-wired). This causes a jarring layout pop from spinner → full grid, and no perceived-performance benefit during the multi-second full-table fetch described in #1.
7. **Unbounded list rendering, no virtualization.** `/conferences` and `/saved` render every filtered/sorted row into a CSS grid with no windowing (no `react-virtual`/`react-window`). At 44+ sources this is likely still hundreds of DOM nodes, each with several nested conditionals (`ConferenceCard` is ~330 lines with heavy conditional branching per card) — will show up as layout/paint cost as the catalogue grows toward the PRD's "200+ active listings" and beyond.
8. **Object-identity-driven `useMemo`/`useCallback` churn**: `filters` is a whole-object `useState`; every `setFilters({ ...filters, x })` call creates a new object, correctly invalidating memos that depend on it, but also means partial filter updates (e.g. toggling one chip) cause the entire `filtered`/`sorted` pipeline to recompute rather than incremental updates — acceptable for now, not scalable indefinitely.

**Low severity / hygiene**

9. **No `React.memo`/key stability issues found** — `key={c.id}` used consistently, no obvious key bugs.
10. **No TypeScript `any` found** in the files read (`grep` didn't surface `: any` in the read set) — types are used carefully throughout (e.g. explicit `SavedRow` interface in `/saved`, typed builder generics in `fetchAllPages<T>`). This is a genuine strength of the codebase, worth preserving in any redesign.
11. **Duplicate/triplicate chip-folding-by-society logic** exists nearly verbatim in `conferences/page.tsx:127-185` and `FilterPanel.tsx:73-108` — same society-folding algorithm implemented twice with slightly different output shapes (one needs counts, one doesn't). Should be a shared helper in `lib/`.
12. **Hydration risk (low, unconfirmed):** `ConferenceCard`'s `isNew` calculation and any `Date.now()`-based logic (`conference-helpers.ts:42`, `ConferenceCard.tsx:108-114`) run in a client component so there's no server/client date mismatch risk for hydration itself — but confirm `new Date().toISOString()` based "today" comparisons don't flicker between SSR-absent client-only renders (they're fine since everything's `'use client'`, just flagging as something to re-check if any of this logic is ever hoisted into a server component during a redesign).
13. **`next.config.ts` is the default scaffold** — no image domains configured, no experimental flags, nothing. If a redesign adds `next/image` for organiser logos or hero art, remote patterns will need configuring.

## 3. Design-system state

**Today: zero design-system abstraction.** There is no `src/components/ui/` primitives layer beyond a single ad-hoc `SaveButton.tsx`. Every component (`ConferenceCard`, `FilterPanel`, `PricingTable`, `ReminderPanel`, `SessionsTable`, page headers, buttons, badges, chips) hand-rolls its own Tailwind utility string per instance. Concretely:

- **Colour:** no design tokens beyond the handful of CSS custom properties in `globals.css:4-46` (`--color-primary-*`, `--color-accent`, `--color-success`, `--color-warning`, `--color-error`) — and **those tokens are barely used**; almost every component instead hardcodes Tailwind slate/cyan/teal/rose/amber/emerald/violet/fuchsia utility classes directly (e.g. `bg-cyan-500/20 text-cyan-300 border-cyan-500/50` repeated near-verbatim across `conferences/page.tsx`, `FilterPanel.tsx`, `ConferenceCard.tsx`). Semantic colour meaning (accredited=emerald, warning=amber, destructive=rose, courses=violet, on-demand=fuchsia, workshops=amber) is consistent by convention but not enforced by any token/variant system — a rename or theme change means a grep-and-replace across ~6 files.
- **Spacing/typography:** `--space-*` custom properties defined in `globals.css` are **not referenced anywhere** in the components read (all spacing is literal Tailwind `p-4`/`gap-2`/`px-3.5` etc.) — dead tokens.
- **Component reuse vs duplication:** badge/chip/button patterns (rounded-full pill filters, glass-card containers, gradient CTA buttons) are copy-pasted with minor variations at each call site rather than parameterized components. `glass-card` (a real reusable CSS class) is the one consistently reused primitive. Button styling for primary CTAs (`bg-gradient-to-r from-cyan-500 to-teal-500 ...`) appears near-identically in `Navbar.tsx`, `saved/page.tsx`, `conferences/[id]/page.tsx` — a prime `<Button variant="primary">` extraction candidate.
- **What a `ui/` primitives layer needs**, given current usage patterns: `Button` (primary gradient / outline-slate / destructive-rose variants — seen ×6+ call sites), `Badge`/`Pill` (status chips: CPD, course/workshop/on-demand/new tags, filter chips — seen ×10+ call sites with near-identical pill styling), `Card` (`glass-card` is already a CSS class, just needs a component wrapper with slots), `Input`/`SearchBar` (already a dedicated component, could become the `Input` primitive), `Select` (native `<select>` styled ad-hoc in 4+ places — `conferences/page.tsx`, `FilterPanel.tsx`, `ReminderPanel.tsx`, `saved/page.tsx` — a real Radix `Select` would fix the ugly native-select dropdown OS-chrome that appears despite the `appearance-none` class), `Tabs` (PricingTable's band/sub tabs are hand-rolled state, `PricingTable.tsx:77-145`), `Skeleton` (CSS exists, unused — wire it up), `Sheet`/`Drawer` (mobile filter panel today is just a stacked block under the search bar — `FilterPanel` isn't collapsible/off-canvas on mobile, a real gap), `Calendar` (needed fresh for the proposed feature, see §4), `Toast` (no toast/snackbar system exists anywhere — errors like `ReminderPanel`'s inline red box (`ReminderPanel.tsx:276-281`) are the only feedback pattern; adding real toasts would unify error/success feedback across save/reminder/auth actions).

**shadcn/ui + Radix feasibility:** Not installed today (`package.json` has no `@radix-ui/*`, no `class-variance-authority`, no `tailwind-merge`, no `clsx`). Given Tailwind v4 is already in place, shadcn/ui's CLI (`npx shadcn@latest init`) supports Tailwind v4 as of its 2025 releases (CSS-variable-based theming maps cleanly onto the existing `:root` custom-property pattern in `globals.css` — the redesign could literally extend that same block). Cost of adoption is low-to-moderate: ~4 new deps (`radix-ui` primitives are added per-component, `cva`, `clsx`/`tailwind-merge`), and every hand-rolled `<select>`/pill/button above maps to an existing shadcn recipe (`select`, `badge`, `button`, `tabs`, `sheet`, `skeleton`, `sonner` for toasts). Given how much ad-hoc, repeated, slightly-inconsistent utility-class styling already exists (§3 above), **adopting shadcn/ui is the recommended path over continuing hand-rolled components** — it directly replaces the biggest duplication pain points (buttons, pills/badges, selects) with accessible, keyboard-correct primitives (native `<select>` today has no way to get a nicer dropdown without Radix), and a Tailwind-v4-first codebase with zero existing component library means there's no migration cost for existing shadcn components to fight with — this is a greenfield adoption, not a retrofit.

## 4. Calendar feature feasibility

**Data model: no new tables needed.** Everything required already exists:
- `saved_conferences` (`supabase_schema.sql:205-213`, RLS-protected, indexed on `user_id` and `conference_id` — `:283-284`) gives the user's saved-event set.
- `conferences.start_date`/`end_date` (and `course_sessions.start_date`/`end_date` for multi-session courses, `abstract_deadline` for the secondary deadline event) give the dates to plot.
- `useSaved()` (`src/hooks/useSaved.ts`) already gives `savedIds`; `/saved/page.tsx` already does the saved-id → full conference row join (currently ad-hoc, see risk #3 above — worth extracting into a shared hook, e.g. `useSavedConferences()`, that both `/saved` and a new `/calendar` page consume, rather than a third copy of the fetch/pagination logic).
- `lib/ics.ts` already generates a per-conference `.ics` file (`generateIcs`, `downloadIcs`) with a conference VEVENT + an abstract-deadline VEVENT — this is single-event export only (one file per conference, triggered from the detail page). For a calendar *view* feature you don't need to touch this file at all (it solves "export to external calendar app," not "see my saved events in an in-site grid") — but it's worth knowing it exists so a future "export my whole saved calendar" (one `.ics` with N VEVENTs) is a small extension of the same module rather than new code.
- `user_reminders` (`supabase_schema.sql:232-246`) is a separate, day-precision "notify me" system (already has its own UI: `ReminderPanel.tsx`) — not needed for rendering a calendar grid, but if the calendar view wants to show reminder markers alongside saved-event markers, the table's already there and already user-scoped.

**Minimal implementation shape:**
1. New route `/calendar` (protected, alongside `/saved`), client component.
2. Reuse (after extracting) the saved-conferences fetch hook to get `Conference[]` for the signed-in user.
3. Build a `{ 'YYYY-MM-DD': Conference[] }` map from `start_date`/`end_date` (span multi-day events across each date in range — the existing `ics.ts:dayAfter` helper shows the date-math pattern already used elsewhere in the codebase) plus, optionally, a second map for `abstract_deadline` markers.
4. Render a month grid; clicking a day with events shows a popover/list of that day's saved conferences linking to `/conferences/[id]`.

**Build vs. library recommendation: build a lightweight custom month grid, do not add FullCalendar/react-big-calendar.**
- **Scope fit:** the ask is "see saved conferences marked on a month/week grid" — not drag-to-reschedule, not resource views, not recurring events, not multi-calendar overlay. That's a small fraction of what FullCalendar or react-big-calendar solve; both are built for apps where the calendar *is* the primary editing surface (e.g. booking systems), which MedConf explicitly is not (CLAUDE.md: "Out of scope: booking").
- **Bundle cost:** `@fullcalendar/react` + core + plugins is commonly 150–250KB+ min+gzip for the pieces needed (daygrid alone is non-trivial; timegrid/interaction plugins add more) — heavy for a feature that's a secondary view of data the app already renders as cards. `react-big-calendar` is lighter (~tens of KB) but drags in `moment`/`date-fns` as a peer dependency and its default styling is heavily Bootstrap-flavored, meaning significant CSS override work to match the existing slate/cyan glass-morphism aesthetic — fighting the library's own stylesheet is real ongoing cost. `schedule-x` is a reasonable newer, framework-agnostic, lighter alternative if a library is wanted, but still pulls in a scheduling-app mental model and its own theming system to override.
- **Tailwind v4 compatibility:** none of the three libraries above ship Tailwind-native styling — all require wrapping/overriding their own CSS, which is friction against a codebase that is 100% Tailwind-utility-driven today (zero other CSS files besides `globals.css`).
- **A custom grid is genuinely small:** a month view is a 6×7 `<div>` grid (42 cells, some from adjacent months), dates computed with plain `Date` math (the codebase already has exactly this kind of date arithmetic in `lib/ics.ts` and `lib/conference-helpers.ts` — no new date library needed, definitely don't add `moment`), each cell rendering a day number + up to N truncated event chips (reusing the existing pill/badge visual language) + a "+2 more" overflow affordance. Week view, if wanted, is the same grid logic with 7 cells instead of 42. This is roughly a `CalendarGrid` component (~150–250 lines) in the same style as `SessionsTable.tsx`/`PricingTable.tsx`, not a multi-day project, and it stays visually and architecturally consistent with everything else in `src/components/conferences/`.
- **Recommendation:** build it custom under `src/components/calendar/`, styled with existing Tailwind conventions and the (soon-to-exist) `ui/` primitives (`Badge` for event chips, `Card`/`glass-card` for the grid container). Revisit a library only if week/day timed views or drag-and-drop rescheduling become real requirements later.

---

**Summary:** the app is a fully client-rendered, client-filtered directory with solid typing and a working URL-synced filter pattern, but it downloads entire tables into the browser on every visit with no caching and no design-system layer — every visual element is hand-rolled Tailwind, duplicated across 3–6 call sites. A redesign should land a shadcn/ui-based `ui/` primitives layer first, then dedupe the data hooks (which also unblocks a cheap, custom-built calendar feature — no new tables, no calendar library needed), and treat moving search/filter/sort to the database as the one true architectural fix rather than a nice-to-have.
